# AI Agent 파헤치기 3 · 멀티에이전트는 어떻게 적용할까?

> 업로드용 예제 자료 · Agentic AI 2기 노드 요약본에서 사진만 뺀 사본입니다.

## 멀티 에이전트 (Multi-agent · 리드(lead)와 워커(worker))

하나의 작업을 여러 에이전트에게 나눠 맡기고 각자의 결과를 합쳐 완성하는 실행 구조. 일을 나누고 합치는 쪽을 리드, 나뉜 몫을 처리하는 쪽을 워커라고 부른다.

### 왜 필요한가

에이전트 하나에 큰 조사를 통째로 맡기면 검색 자료와 중간 판단이 컨텍스트(에이전트가 다음 행동을 고를 때 함께 읽는 지시·대화·파일·도구 결과)에 계속 쌓인다. 쌓일수록 처음 질문은 뒤로 밀리고 앞서 찾은 근거도 다시 찾기 어려워진다. 그래서 일을 나눠 컨텍스트 윈도우(한 번에 읽을 수 있는 범위)를 여러 개 쓰자는 생각이 나온다.

### 무엇인가

보통 순서는 이렇다. ① 리드가 워커 역할을 미리 정의해 둔다 ② 한 번의 위임으로 여러 워커를 동시에 실행한다 ③ 워커는 자기 몫만 처리한다 ④ 리드가 결과를 합친다. Anthropic의 Research 시스템이 대표 예다. 리드 에이전트는 자기 컨텍스트가 200,000토큰을 넘으면 잘릴 수 있어서, 시작할 때 연구 계획을 별도 메모리에 저장해 둔다.

나누면 세 가지 이점이 생긴다. ① 병렬 탐색: 워커들이 각자 분리된 컨텍스트에서 다른 질문을 동시에 살피고 필요한 결과만 간추려 넘기므로, 리드는 탐색 기록 전체를 다시 읽지 않고 비교 재료만 받는다. ② 관심사 분리: 워커마다 도구·프롬프트·탐색 과정을 따로 두어, 앞선 검색 결과에 끌려 판단이 바뀌는 '경로 의존성'이 줄어든다. ③ 전문화: 자료 찾기, 반례 찾기, 인용 위치 확인처럼 워커에게 책임 하나씩을 준다. 세 이점 모두 하나의 긴 컨텍스트를 서로 독립적인 증거 묶음으로 나누는 데서 나온다.

대신 나누면 커지는 실패도 있다. 중복: 역할 경계가 흐려 두 워커가 같은 질문을 조사해 비용만 는다. 누락: 어느 워커에게도 맡기지 않은 경계 밖 질문은 아무도 확인하지 않는다. 오류 전파: 한 워커의 잘못된 판단이 요약을 거치며 더 그럴듯한 결론이 되어 최종 결과에 들어간다. 그래서 반환물마다 근거와 불확실성을 남겨야 합친 뒤에도 다시 확인할 수 있다.

비용도 크다. Anthropic 사례에서 멀티 에이전트는 일반 채팅보다 약 15배 많은 토큰을 썼다(단일 에이전트는 채팅의 약 4배). 단일 에이전트 대비 15배가 아니라는 점에 주의한다. 또 리드가 모든 워커가 끝나길 기다린 뒤 다음 단계로 가는 동기 실행이면, 한 워커가 늦을 때 전체가 기다린다.

**기대와 회의**

| 입장 | 주장 | 근거 |
|---|---|---|
| 기대 | 에이전트 수를 늘리면 성능이 오른다 | 여러 에이전트 답을 다수결로 정하는 단순한 방법만으로도 수를 늘릴수록 성능이 오르는 경향(More Agents Is All You Need). Anthropic: 멀티 에이전트 연구 시스템이 단일보다 내부 평가에서 90.2% 높고, 복잡한 질의의 연구 시간을 최대 90% 단축 |
| 회의 | 비용과 혼란만 는다 | Cognition: 에이전트 사이에 컨텍스트가 충분히 공유되지 않아 취약해짐 → 단일 흐름 권장. 해커뉴스 사례: 에이전트 6개짜리 주식 조사 시스템이 질의 하나에 약 2달러, 간단한 질문 하나에 3달러·3분 |

**나눌 조건과 나누지 않을 조건**

| 판정 항목 | 나눌 조건 | 나누지 않을 조건 |
|---|---|---|
| 질문의 독립성 | 서로의 중간 결과 없이 시작할 수 있음 | 앞 결과가 다음 질문을 정함 |
| 컨텍스트 | 자료가 섞이면 처음 기준이 밀림 | 한 흐름에서 함께 비교해야 함 |
| 책임 경계 | 워커별 목표·반환 형식을 정할 수 있음 | 누가 무엇을 확인할지 갈리지 않음 |
| 합성 검토 | 근거·불확실성을 대조할 시간이 있음 | 합치는 비용이 조사 이득보다 큼 |
| 대기 위험 | 한 결과가 늦어도 다른 탐색은 진행 | 하나가 늦으면 전체 판단이 멈춤 |
| 비용 가치 | 추가 토큰 비용을 감당할 이유가 있음 | 짧은 확인만으로 충분 |

### 정리하면

- 이 표는 에이전트 수의 우열을 가리는 표가 아니다. 핵심은 '나눴을 때 결과를 확인하기 쉬워지는가, 그 이득이 조정 비용보다 큰가'다. 나누지 않기로 한 판단도 중요한 결과다.
- 에이전트를 나눈다고 능력이 더해지는 게 아니라, 어느 에이전트가 어떤 컨텍스트를 갖고 무엇을 확인할지가 새로 정해질 뿐이다.
- Anthropic의 두 숫자는 다른 것을 잰 값이다. 90.2%는 단일 대비 성능 차이, 최대 90%는 연구 시간 감소 폭이다.

### 배운 것

- 스텝 1 · 멀티 에이전트의 이점과 비용: 멀티 에이전트의 세 이점(병렬 탐색·관심사 분리·전문화)이 긴 컨텍스트를 독립적인 증거 묶음으로 나누는 데서 나오고, 대가로 중복·누락·오류 전파와 채팅 대비 약 15배 토큰 비용이 생긴다는 것, 나누기 전 여섯 항목(독립성·컨텍스트·책임 경계·합성 검토·대기 위험·비용 가치)으로 판정한다는 것을 배웠다.

관련 항목: 멀티 에이전트 네 구조, 서브에이전트, 컨텍스트 · 컨텍스트 윈도우, A·B·C 비교 실험, 채택 · 축소 · 폐기

## 멀티 에이전트 네 구조 (오케스트레이터-워커 · 팬아웃·합성 · 비평-수정 · 핸드오프)

여러 에이전트를 잇는 대표 방식 네 가지. 누가 일을 나누고, 결과가 어디로 모이며, 틀린 결과를 누가 되돌리는지가 서로 다르다.

### 왜 필요한가

'멀티 에이전트'라는 말은 에이전트가 여럿이라는 뜻일 뿐, 누가 일을 나누고 누가 다음 행동을 정하는지는 알려 주지 않는다. 워커 수가 같아도 연결 방식에 따라 중복 조사, 대기, 잘못된 인계처럼 다른 실패가 생긴다.

### 무엇인가

소통 경로로 크게 둘로 나뉜다. 허브형은 모든 소통이 리드를 거친다. 리드가 나누고 결과를 받아 합친다(오케스트레이터-워커, 팬아웃·합성). 직접형은 에이전트끼리 결과나 제어권을 바로 주고받는다(비평-수정, 핸드오프).

오케스트레이터-워커: 리드(오케스트레이터, 지휘자)가 전략을 세워 위임하고 워커들이 병렬로 탐색한 뒤 리드가 합성한다. Anthropic Research가 쓰는 구조로, 독립된 조사 질문이 여럿인 열린 작업에 맞다. 팬아웃·합성: 같은 출발점에서 여러 워커가 독립 조사하고(팬아웃 = 부채꼴로 펼침) 리드가 비교해 합친다. 자료 수집이나 관점 비교에 맞다.

비평-수정: 초안을 쓰면 비평 담당이 근거 부족·누락·과도한 일반화를 찾아 돌려주고 작성자가 고친다. 반례 점검, 설계안 검토에 맞다. 핸드오프: 앞 담당이 다음 담당에게 제어권을 직접 넘긴다(예: 고객 접수 담당 → 환불 담당). 역할 전환이 필요한 대화에 맞다.

**구조별 위험과 대책**

| 구조 | 주요 위험 | 대책 |
|---|---|---|
| 오케스트레이터-워커 | 모호한 위임으로 중복 조사·근거 없는 결과, 동기 실행 시 대기 병목 | 위임할 때 목표·출력 형식·도구·출처 지침·작업 경계를 먼저 적는다 |
| 팬아웃·합성 | 결과를 그대로 이어 붙여 같은 근거 반복·관점 누락 | 결과 개수보다 근거 겹침과 빈 관점을 확인 |
| 비평-수정 | 끝없는 되돌림 | 확인 항목과 되돌릴 횟수를 미리 정함. 비평이 항상 더 정확하다고 보지 않음 |
| 핸드오프 | 잘못된·반복 인계 | 넘길 조건·되돌릴 조건을 기록. 확인한 사실과 남은 질문을 함께 넘김 |

### 정리하면

- 구조를 고를 때는 결과가 어디로 모이는지, 틀린 결과를 누가 되돌리는지부터 본다.

### 배운 것

- 스텝 2 · 네 가지 구조와 맞는 작업: 허브형(오케스트레이터-워커, 팬아웃·합성)과 직접형(비평-수정, 핸드오프) 네 구조의 동작·맞는 작업·위험·대책을 배우고, 오늘 실습의 C 실행이 '워커가 하나인 오케스트레이터-워커'라는 것을 확인했다.

관련 항목: 멀티 에이전트, 서브에이전트, A2A

## 서브에이전트 (Subagent · 리드가 불러 쓰고 결과만 돌려받는 보조 에이전트)

리드 에이전트가 필요할 때 불러 쓰는 워커 에이전트. 자기 좁은 컨텍스트에서 일하고 결과를 리드에게 돌려준 뒤 끝난다.

### 왜 필요한가

리드가 모든 탐색을 직접 하면 자기 컨텍스트가 탐색 기록으로 가득 찬다. 탐색을 서브에이전트에게 맡기면 리드는 정리된 보고만 받으므로 컨텍스트를 깨끗하게 유지할 수 있다.

### 무엇인가

Claude Agent SDK에서는 ClaudeAgentOptions의 agents 항목에 AgentDefinition을 넣어 서브에이전트의 프롬프트·도구·모델을 정한다. 실습의 locator는 '읽기 전용 탐색 담당'으로, Read·Grep·Glob 도구만 쓰고 파일 경로·함수 이름·한 문단 진단을 보고한다.

서브에이전트는 결과를 리드에게만 돌려준다. 실습에 쓴 claude-agent-sdk 0.2.151의 공개 인터페이스에는 서브에이전트끼리 직접 메시지를 주고받는 방법이 없어서, 실습 구조는 모두 허브형이다.

Claude Code 터미널에서는 마크다운 파일 하나로 같은 역할을 정의한다. .claude/agents/(프로젝트용) 또는 ~/.claude/agents/(모든 프로젝트용)에 파일을 두고, 머리 부분 YAML(이름: 값 형식의 설정)에 name·description(필수), tools, model, maxTurns를 적는다. 그 아래 본문이 시스템 프롬프트다. OpenCode는 .opencode/agents/에 두며 파일 이름이 에이전트 이름이 되고, mode: subagent로 보조 에이전트임을 표시하고 permission으로 도구를 제한한다.

### 정리하면

- 서브에이전트를 정의했다고 분업이 일어난 건 아니다. 리드가 locator를 한 번도 부르지 않고 Grep·Read로 직접 탐색하는 경우가 흔하다. 실제로 불렀는지는 트랜스크립트로 확인한다.
- Claude는 요청과 description을 견줘 맡길지 스스로 정한다. 반드시 맡기려면 프롬프트에 @agent-locator 를 쓴다.
- 세션을 시작할 때 agents 폴더가 없었다면, 폴더와 첫 파일을 만든 뒤 세션을 다시 시작해야 반영된다.
- CLI에서 서브에이전트를 부르면 result.json 같은 실험 기록이 자동으로 남지 않으므로, 비교하려면 비용·턴 수·수정 범위를 직접 적는다.

```
---
name: locator
description: 버그 보고를 받아 원인이 있는 파일 경로·함수 이름·진단을 구조화된 보고로 남긴다. 파일을 고치지 않는다.
tools: Read, Grep, Glob
model: haiku
maxTurns: 12
---

당신은 읽기 전용 탐색 담당입니다. 저장소를 읽고 검색만 하며, 결과는
파일 경로 · 함수 또는 클래스 이름 · 한 문단 진단의 세 항목으로 보고합니다.
```
Claude Code용 locator 정의 파일(.claude/agents/locator.md). tools에 읽기 도구만 적어 파일을 고칠 수 없게 한다.

### 배운 것

- 스텝 6 · 모델이 정하는 흐름: 리드가 나누기: AgentDefinition으로 읽기 전용 locator를 정의하고 agents={'locator': ...}로 리드 세션에 등록하는 법, 그리고 서브에이전트를 정의해도 리드가 부르지 않을 수 있으므로 트랜스크립트에서 subagent_type 기록을 세어 확인해야 한다는 것을 배웠다.
- 스텝 9 · 오늘의 locator를 CLI 서브에이전트로 정의하기: 같은 locator를 Claude Code(.claude/agents/, name·description·tools·model·maxTurns)와 OpenCode(.opencode/agents/, mode: subagent, permission) 마크다운 파일로 정의하는 법과, CLI에서는 실험 기록이 자동으로 남지 않는다는 차이를 배웠다.

관련 항목: 멀티 에이전트, Claude Agent SDK, 에이전트 팀, 세션 JSONL 트랜스크립트

## A2A (Agent2Agent Protocol · 소유자가 다른 에이전트끼리 통신하는 공개 규약)

서로 다른 회사·프레임워크가 만든 에이전트들이 일을 주고받을 수 있게 정한 공개 프로토콜. Google이 2025년 4월 발표했고 Linux Foundation에 기증되어 기술 운영 위원회(TSC)가 관리한다.

### 왜 필요한가

실습의 리드와 워커는 같은 실행 환경 안에 있어서, 권한과 결과 위치를 이미 알고 내부 호출만으로 협업한다. 하지만 다른 부서나 다른 회사의 에이전트에게 일을 맡기려면 '어디로 요청하나, 상대가 무슨 일을 받나, 끝났는지 어떻게 아나, 결과물은 어디 있나'를 미리 합의해야 한다.

### 무엇인가

세 층으로 이뤄진다. ① 발견: 상대 에이전트는 Agent Card라는 JSON 문서로 이름·접근 URL·인증 방식·기능을 선언한다. 선언일 뿐이므로 실제 권한과 품질은 따로 검증한다. ② 작업: 의뢰 쪽이 task를 보내고 submitted(요청됨)·working(작업 중)·completed(완료)·failed(실패) 같은 상태를 추적한다. ③ 결과물: 답변 문장 대신 파일이나 구조화된 데이터를 담은 artifact로 돌려준다. '완료'라는 상태와 '무엇이 만들어졌는지'를 구분하기 위해서다.

요청 순서는 ① 의뢰 에이전트가 Agent Card 확인 ② task 전송 ③ 수행 에이전트가 submitted → working → (필요하면 input-required) 순으로 상태 갱신 ④ 완료되면 artifact 반환 ⑤ 의뢰 에이전트가 검증 후 다음 작업 결정이다.

### 정리하면

- 도입 여부는 'A2A를 지원하는가'가 아니라 '우리 작업에 독립된 외부 에이전트가 실제로 있는가'로 판단한다. 같은 하네스 안에서 서브에이전트를 짧게 부르면 기존 구조가 더 단순하다. 부서·공급자가 다르고 내부 구현을 감춘 채 반복해서 일을 주고받는다면 A2A가 맞다.
- Agent Card JSON은 기능 선언 초안일 뿐이다. 맡겨도 되는지 판단하려면 기능마다 입력 범위, 반환 artifact, 사람 승인 지점, 허용하지 않는 권한을 덧붙인다.

### 배운 것

- 스텝 2 · 깊이 보기: A2A: A2A가 소유자·프레임워크가 다른 에이전트 사이의 공개 통신 규약이며, 발견(Agent Card)·작업(task 상태)·결과물(artifact) 세 층과 다섯 단계 요청 순서로 동작하고, 도입은 독립된 외부 에이전트가 실제로 있는지로 판단한다는 것을 배웠다.

관련 항목: 멀티 에이전트 네 구조, 서브에이전트

## Claude Agent SDK (claude-agent-sdk · Claude Code의 기능을 파이썬에서 쓰는 개발 도구)

Claude Code가 가진 도구 실행·권한·세션 기록·서브에이전트 정의·구조화 출력을 파이썬 코드에서 호출할 수 있게 해 주는 라이브러리. SDK(Software Development Kit)는 프로그램을 만들 때 쓰는 부품 묶음이다.

### 왜 필요한가

A·B·C 세 방식을 공정하게 비교하려면 모델·도구·기록 형식은 똑같이 두고 '다음 행동을 정하는 주체'만 바꿔야 한다. 대화형 CLI를 스크립트로 반복 호출하면 사람 조작과 셸 환경이 끼어들어 조건 고정이 어렵고, Messages API를 직접 부르면 도구 실행기·권한 승인·기록 형식을 전부 직접 만들어야 하며, LangGraph 같은 범용 프레임워크는 비교하려는 결정 주체가 프레임워크 안에 가려진다.

### 무엇인가

query() 함수에 프롬프트와 ClaudeAgentOptions를 넘기면 에이전트가 실행되고 메시지가 차례로 흘러나온다. 마지막에 오는 ResultMessage에 비용·턴 수 같은 결과가 담긴다.

실습에서 쓴 옵션들: cwd(작업 폴더), model='haiku', max_turns(턴 예산), system_prompt(역할 지시), permission_mode='bypassPermissions'(도구 실행마다 승인을 묻지 않음), setting_sources=[](내 PC의 Claude Code 설정·CLAUDE.md·플러그인·훅을 불러오지 않아 사람마다 다른 설정이 섞이지 않게 함), allowed_tools(묻지 않고 자동 승인할 도구 목록), agents(서브에이전트 등록), forward_subagent_text=True(서브에이전트의 텍스트·사고 블록까지 메시지 스트림에 넣음).

주의: allowed_tools는 '자동 승인할 도구 목록'일 뿐 다른 도구를 막지 않는다. B의 locator가 파일을 고치지 않는 것은 지시문을 따른 결과이므로 실제로 확인해야 할 관찰 항목이다.

### 정리하면

- 시스템 파이썬 대신 가상 환경(프로젝트 전용으로 분리된 파이썬 설치 공간)을 쓴다. 실험 환경이 섞이지 않고, PEP 668(운영체제가 관리하는 파이썬에 pip 설치를 막도록 표시하는 규격) 때문에 전역 설치가 막히는 문제도 피한다.
- max_turns를 다 쓰면 SDK가 오류를 던진다. 실습 코드는 이를 except로 잡아 멈추지 않고 '턴 소진'을 관측 결과로 남겨 채점했다.
- PowerShell에서 결과 파일을 볼 때는 Get-Content 파일 -Encoding UTF8 을 쓴다. 빼면 한글이 깨질 수 있다.

```
python --version
python -m venv .venv
.venv\Scripts\python.exe -m pip install claude-agent-sdk pytest mpmath
```
실험 폴더에 전용 가상 환경(.venv)을 만들고 SDK를 설치한다. claude-agent-sdk는 파이썬 3.10 이상에서만 설치된다.

### 배운 것

- 스텝 4 · 왜 Claude Agent SDK인가: 대화형 CLI 반복 호출·Messages API 직접 호출·범용 프레임워크와 비교해 SDK가 모델·도구·기록 형식을 같게 두고 결정 주체만 바꿀 수 있다는 이유, .venv 가상 환경 설치(파이썬 3.10 이상), 그리고 bypassPermissions·setting_sources=[]·allowed_tools 같은 옵션의 뜻을 배웠다.

관련 항목: A·B·C 비교 실험, 서브에이전트, 턴 예산, 세션 JSONL 트랜스크립트

## A·B·C 비교 실험 (기준선(A) · 워크플로(B) · 오케스트레이션(C))

같은 버그 문제를 '다음 행동을 누가 정하는가'만 바꾼 세 방식으로 풀어 비교한 실습. A는 에이전트 하나, B는 파이썬 코드가 순서를 정하고, C는 리드 모델이 스스로 정한다.

### 왜 필요한가

멀티 에이전트가 더 낫다는 발표와 오히려 해롭다는 주장이 엇갈린다. 발표만 읽어서는 어느 쪽이 내 조건에서 맞는지 알 수 없다. 같은 문제를 조건만 바꿔 직접 돌리고 기록을 비교해야 판정할 수 있다.

### 무엇인가

문제는 SymPy(파이썬 수학 계산 라이브러리)의 실제 버그 3개다. sympy-24909는 접두사에 단위를 곱하면 결과가 1이 되어 단위가 사라지는 버그(milli * W가 밀리와트가 되어야 함), sympy-24213은 가속도×시간에 속도를 더하면 같은 차원(길이·시간·속도 같은 물리량의 종류)인데도 오류가 나는 버그, sympy-24152는 텐서곱(두 대상을 짝지어 결합하는 연산)의 인수에 덧셈이 섞이면 전개가 덜 되는 버그다. 문제는 git clone https://github.com/SunCreation/d035-agent-lab.git 으로 받는다.

세 방식: ① 기준선 실행 A: 에이전트 하나가 최대 25턴 안에 탐색과 수정을 모두 한다. ② 워크플로 실행 B: 파이썬 코드가 'locator(읽기 전용 탐색, 12턴) → fixer(보고를 받아 수정, 18턴)' 순서를 고정한다. 두 세션은 대화를 공유하지 않고 코드가 정한 보고서(locate_report)만 넘어간다. ③ 오케스트레이션 실행 C: 리드 모델이 최대 40턴 동안 직접 고치되, 필요하면 locator 서브에이전트를 부를지 스스로 정한다.

고정한 조건은 문제, 모델 별칭(haiku, 실행 시점의 최신 Haiku 모델), 저장소 준비 방식, 채점 방식이다. 달라진 조건은 조율 방식과 턴 예산(25 / 12+18 / 40)이다. 턴 예산이 같지 않으므로 숫자 하나로 구조의 우열을 정할 수 없다.

평가는 공식 SWE-bench 도커 평가가 아닌 경량 평가다. info.json의 기준 커밋으로 SymPy를 받고, 에이전트가 고친 복사본에 test_patch.diff(확인용 테스트를 더하는 패치)를 적용해 대상 테스트 한두 개만 실행한다. 정답 패치는 주어지지 않는다.

**결과 폴더 runs/<방식>-<문제>/ 에 남는 것**

| 파일·필드 | 뜻 |
|---|---|
| resolved | 대상 테스트 종료 코드가 0인지(통과 여부) |
| invalid | tests/ 아래 파일을 바꿨는지(바꿨으면 무효) |
| cost_usd, num_turns, wall_s | 비용(달러), 대화 턴 수, 경과 시간(초). B는 두 호출 합 |
| final_text / tail / error / extra | 마지막 응답 / 테스트 출력 끝부분 / 오류(턴 소진 포함) / 실행별 추가 기록(B의 locate_report 등) |
| changes.diff | 에이전트가 수정한 내용 |
| transcript*.jsonl | 세션 트랜스크립트 복사본(서브에이전트 기록 포함) |

### 정리하면

- 실험 스크립트는 코딩 에이전트에게 만들게 했다. 모두 같은 구조가 되도록 공통 설정과 A·B·C 코드를 참고코드.md에 넣고 '글자 하나 바꾸지 말고 그대로 쓰라'고 지시했다. 파일은 arms.py(실행)와 common.py(문제 준비와 채점) 두 개다.
- 실행: .venv\Scripts\python.exe arms.py A sympy__sympy-24909 (문제 하나), .venv\Scripts\python.exe arms.py A,B,C (세 문제 × 세 방식). result.json이 이미 있는 실행은 건너뛴다. 다시 돌리려면 기존 폴더를 지우지 말고 다른 이름으로 옮겨 둔다.
- C에서 리드가 locator를 실제로 불렀는지는 트랜스크립트에서 "subagent_type":"locator" 문자열이 있는 줄 수로 센다. 'locator'라는 단어만 세면 안 된다. 사용 가능한 에이전트 목록에도 이름이 남아 있어 안 불렀어도 0이 나오지 않는다.
- sympy-24909는 버그를 고치고도 테스트에서 자주 떨어진다. 예를 들어 SymPy의 S.One 대신 파이썬 정수 1을 돌려주면 겉보기 결과는 맞아도 테스트의 비교 검사에 걸린다. 실패하면 tail에서 어떤 검사에 떨어졌는지 본다.
- 턴 소진도 단순 오류가 아니라 어디까지 탐색했고 어디서 멈췄는지 보여 주는 기록이다.

### 배운 것

- 스텝 4 · 단일 에이전트로 기준선 세우기: SymPy 문제 3개를 받아 A(에이전트 하나, 25턴)로 기준선을 세우고, result.json·changes.diff·transcript*.jsonl에 남는 필드의 뜻을 배웠다.
- 스텝 5 · 코드가 정하는 흐름: 워크플로로 나누기: B에서 파이썬 코드가 locator(Read·Grep·Glob, 12턴) → fixer(18턴) 순서를 고정하고 locate_report만 넘긴다는 것, allowed_tools는 자동 승인 목록일 뿐 다른 도구를 막지 않는다는 것을 배웠다.
- 스텝 6 · 모델이 정하는 흐름: 리드가 나누기: C에서 리드 모델이 locator 호출 여부를 스스로 정하며(최대 40턴), 호출 여부를 트랜스크립트의 subagent_type 기록으로 확인해야 한다는 것을 배웠다.
- 스텝 8 · 단일과 멀티 비교 판정하기: 고정 조건(문제·모델·저장소 준비·채점)과 달라진 조건(조율 방식·턴 예산)을 나눠 읽고, 세 점수가 비슷하면 num_turns·cost_usd·diff 크기 같은 행동의 양으로 차이를 읽으며, 결론은 'SymPy 3문제·이 조건'에서만 말한다는 것을 배웠다.

## 턴 예산 (max_turns · 에이전트가 모델 응답과 도구 실행을 주고받을 수 있는 최대 횟수)

에이전트가 '모델이 행동을 고르고 → 도구가 실행하고 → 결과를 돌려받는' 한 바퀴를 최대 몇 번까지 돌 수 있는지 정한 상한.

### 왜 필요한가

에이전트가 같은 탐색을 끝없이 반복하면 비용과 시간이 한없이 늘어난다. 턴 예산은 그 상한을 정해 준다. 동시에 비교 실험에서는 예산이 다르면 결과 차이가 구조 때문인지 예산 때문인지 가를 수 없게 되므로, 예산이 같은지 꼭 확인해야 하는 조건이기도 하다.

### 무엇인가

실습의 예산은 A 25턴, B locator 12턴 + fixer 18턴, C 리드 40턴이었다. 서로 같지 않으므로 해결 여부·비용·시간만 놓고 구조의 효과라고 해석할 수 없다.

교안을 쓸 당시엔 A가 25턴을 다 쓴 경우가 있었지만 최근 모델은 대개 10턴 안팎에서 끝났다. 턴을 다 쓰면 SDK가 오류를 던지는데, 실습 코드는 이를 '턴 소진'이라는 관측 결과로 남겼다.

### 정리하면

- 비교표를 읽을 때 턴 예산 차이를 '달라진 조건'으로 따로 표시한다.

### 배운 것

- 스텝 3 · 비교 실험을 채점하는 방법: 문제·모델은 같아도 턴 예산(max_turns)이 A 25, B 12+18, C 40으로 달라서 차이를 실행 방식만의 효과로 읽으면 안 되고, 고정 조건과 달라진 조건을 나눠 읽어야 한다는 것을 배웠다.

관련 항목: A·B·C 비교 실험, Claude Agent SDK

## LLM judge · 두 층 채점 (LLM-as-a-judge · 루브릭(rubric) · evidence_quote)

언어 모델에게 정해진 기준표(루브릭)를 주고 실행 기록을 평가하게 하는 방식. 실습에서는 테스트 통과 여부(1층) 위에 행동 과정을 보는 2층 채점으로 썼다.

### 왜 필요한가

테스트는 '통과했나'만 알려 준다. 근거 없이 찍어서 통과한 실행과, 통과는 못 했지만 어디서 막혔는지 잘 남긴 실행을 구별하지 못한다. 기록을 읽고 과정을 평가할 두 번째 눈이 필요하다.

### 무엇인가

1층(결정론적, 언제 돌려도 같은 결과): common.py가 테스트 패치를 적용하고 pytest를 실행해 종료 코드를 직접 받는다. resolved(대상 테스트 통과)와 invalid(테스트 파일을 건드렸나)를 남긴다. 설명이 아무리 좋아도 이 판정을 대신할 수 없다.

2층(LLM judge): judge.py가 각 실행의 result.json과 트랜스크립트를 판정 모델에 보내 세 점수(0·1·2)를 받는다. 근거_추적은 파일을 읽은 뒤 편집했는지, 편집_최소성은 문제와 무관한 변경을 넓히지 않았는지, 검증_성실성은 수정 뒤 확인을 했는지를 묻는다. 여기에 실패 분류와 evidence_quote(판정 근거가 된 트랜스크립트 구절), 한 줄 사유를 더한다.

판정 모델에게 자유 서술을 시키지 않고, output_format의 json_schema로 출력 구조를 못박는다. evidence_quote가 필수 항목이라 인용 없이 '검증을 했다'는 말만으로는 점수를 받을 수 없다. Anthropic의 연구 평가 루브릭(사실 정확성·인용 정확성·완결성·출처 품질·도구 효율성)을 '결과 문장이 그럴듯한가'가 아니라 '수정에 이른 행동 기록'을 읽는 기준으로 바꿔 쓴 것이다.

### 정리하면

- 판정 모델은 실험 모델(haiku)과 다른 모델(sonnet)을 쓴다. 같은 모델이 자기 행동을 채점하면 자기 설명에 끌릴 수 있다. 판정 호출에도 setting_sources=[]를 넣는다.
- 판정이 끝나면 evidence_quote가 실제 트랜스크립트에 있는지 확인해 quote_found(True/False)로 남긴다. False인 행은 점수를 믿지 말고 원래 기록으로 돌아가 확인한다(사전 테스트에서 9건 중 1건이 그랬다).
- pytest | tail 처럼 파이프로 이으면 pytest가 실패해도 마지막 명령 tail의 종료 코드 0이 남아 실패가 가려질 수 있다. 출력 줄이기(보기용)와 종료 코드 판정을 나눈다.
- 실행: .venv\Scripts\python.exe judge.py (판정+집계), judge.py --aggregate (판정은 그대로 두고 집계만 다시). 결과는 실행 폴더마다 judgment.json, 폴더 바로 아래 grading.jsonl과 results-table.md.

### 배운 것

- 스텝 3 · 두 층 채점: 테스트와 LLM judge: 1층 테스트(resolved·invalid)와 2층 LLM judge(근거_추적·편집_최소성·검증_성실성 0~2점, 실패 분류, 필수 evidence_quote)를 함께 봐야 '통과했지만 근거가 약한 실행'과 '실패했지만 막힌 곳을 남긴 실행'을 구별한다는 것, 판정 모델은 실험 모델과 다른 sonnet을 쓴다는 것을 배웠다.
- 스텝 7 · 실행 기록 읽기와 판정: judge.py를 만들어 json_schema로 구조화 출력을 받고 quote_found로 인용 실재 여부를 검사하며, 실행 하나를 result.json → changes.diff → 트랜스크립트 → judgment.json 순서로 읽는 법을 배웠다.

관련 항목: MAST, 세션 JSONL 트랜스크립트, A·B·C 비교 실험

## 세션 JSONL 트랜스크립트 (Session JSONL transcript · JSON Lines)

에이전트 세션이 주고받은 메시지와 도구 호출을 한 줄에 하나씩 JSON으로 적어 둔 기록 파일. JSONL(JSON Lines)은 한 줄에 JSON 객체 하나씩 쓰는 형식이다.

### 왜 필요한가

에이전트가 '이 파일을 읽고 고쳤다'고 말해도, 실제로 무엇을 어떤 순서로 했는지는 기록을 봐야 안다. 트랜스크립트는 그 행동 순서를 그대로 담은 1차 자료다.

### 무엇인가

JSON은 이름과 값을 짝지어 적는 데이터 형식이다. JSONL은 이것을 한 줄에 하나씩 이어 붙여, 기록이 생길 때마다 줄을 덧붙이기 쉽고 한 줄씩 읽어 처리하기도 쉽다.

Claude Code·Agent SDK의 원본 트랜스크립트는 ~/.claude/projects/ 아래에 남는다. 실습의 arms.py는 실행이 끝나면 이를 실행 폴더에 transcript*.jsonl로 복사했고, judge.py는 이 복사본을 읽었다.

### 정리하면

- 기록이 없는 실행에 나중에 설명을 덧붙이지 않는다.
- 특정 행동을 찾을 때는 정확한 문자열로 센다. 예: (Select-String -Path runs\C-sympy__sympy-24909\transcript*.jsonl -Pattern '"subagent_type":"locator"' -SimpleMatch).Count

### 배운 것

- 스텝 3·7 · 세션 JSONL 트랜스크립트: 트랜스크립트가 세션의 메시지와 도구 호출을 한 줄에 하나씩 JSON으로 남긴 파일이며, 원본은 ~/.claude/projects/ 아래에 있고 arms.py가 실행 폴더로 복사해 judge.py가 읽는다는 것을 배웠다.

관련 항목: LLM judge · 두 층 채점, A·B·C 비교 실험

## MAST (Multi-Agent System Failure Taxonomy · 멀티 에이전트 실패 유형 분류)

여러 멀티 에이전트 실행 기록을 분석해 실패를 유형별로 정리한 분류 체계(arXiv 2503.13657). 실습의 LLM judge는 이 계열의 실패 분류 이름을 썼다.

### 왜 필요한가

'실패했다'만 적으면 다음에 무엇을 고칠지 알 수 없다. 실패를 정해진 이름으로 분류해 두면 여러 실행을 모아 어떤 실패가 자주 나는지 셀 수 있다.

### 무엇인가

실습에서 쓴 실패 분류: 턴_소진(예산을 다 씀), 무근거_편집(관련 코드를 읽지 않고 고침), 과잉_편집(문제와 무관한 곳까지 바꿈), 검증_생략(수정 뒤 확인하지 않음), 잘못된_수정(버그는 고쳤지만 테스트가 기대한 동작과 다르게 고침) 등.

### 정리하면

- 실패한 실행은 tail·error·final_text와 changes.diff를 함께 읽어야 어느 분류인지 가를 수 있다. 성공 여부만으로는 구분되지 않는다.

### 배운 것

- 스텝 3 · 두 층 채점: MAST 계열 실패 분류(턴_소진·무근거_편집·과잉_편집·검증_생략·잘못된_수정)를 LLM judge의 출력 항목으로 쓴다는 것을 배웠다.

관련 항목: LLM judge · 두 층 채점, 멀티 에이전트

## Terminal-Bench (터미널에서 주어진 작업을 수행하게 하는 벤치마크)

에이전트에게 터미널 작업(파일 읽기, 데이터 정리, 결과 파일 만들기 등)을 시키고 채점용 테스트로 결과를 확인하는 벤치마크.

### 왜 필요한가

코딩 에이전트의 능력은 기존 코드 고치기만이 아니다. 로그를 세거나 데이터를 걸러 파일로 만드는 일처럼 터미널에서 하는 일반 작업도 따로 재야 한다.

### 무엇인가

선택 실습의 두 문제: log-summary는 서비스 로그 파일들에서 ERROR·WARNING·INFO 줄 수를 세어 summary.csv를 만들고, bank-trans-filter는 회사명·계좌번호에 오타가 섞인 거래 내역에서 특정 회사 거래만 골라 날짜순 output.json을 만든다. 문제 폴더에는 task.yaml(작업 지시문), 입력 데이터, tests/test_outputs.py(채점 테스트)가 있다.

SymPy는 큰 저장소에서 고칠 위치를 찾아야 해서 탐색을 locator에게 맡길 이유가 있다. 반면 이 두 문제는 입력이 로그 파일 3개, CSV 1개뿐이라 에이전트 하나가 전체를 읽을 수 있다. 판정표로 보면 '짧은 확인만으로 충분', '한 흐름에서 함께 비교해야 함'에 가깝다.

### 정리하면

- 실행 전에 판정표 여섯 항목으로 A·B·C의 결과를 먼저 예측해 적고, 실행 후 맞았는지 확인한다. 예측과 다르면 판정표의 어느 항목을 잘못 읽었는지 적는다.
- SymPy 행과 Terminal-Bench 행은 한 표에서 섞어 평균 내지 않는다. 프롬프트와 작업 종류가 바뀌었기 때문이다. 새 파일을 만드는 작업이라 편집_최소성 점수 해석에도 주의한다.

### 배운 것

- 스텝 8 · 깊이 보기: 선택 실습 — Terminal-Bench 문제 2개: 입력이 작아 한 에이전트가 다 읽을 수 있는 Terminal-Bench 2문제로 판정표의 예측('나누지 않을 조건')을 먼저 적고 A·B·C로 실행해 확인하며, 결과는 SymPy와 섞지 않고 '축소' 판정의 근거로 쓸 수 있다는 것을 배웠다.

관련 항목: SWE-bench, A·B·C 비교 실험, 멀티 에이전트

## 멀티 에이전트 보조 도구 (Agent Teams · Workflows · oh-my-claudecode · herdr)

멀티 에이전트를 돌릴 때 드러나는 네 문제(컨텍스트 끊김, 재현 불가, 모델 배분, 상태 가시성)를 각각 겨냥한 최근 도구들. 이름이 아니라 풀려는 문제로 고른다.

### 왜 필요한가

실습을 해 보면 문제가 드러난다. 워커 결과가 리드에게만 돌아가 워커끼리 서로 무엇을 찾았는지 모르고, 리드가 매번 다른 경로를 밟아 재현이 안 되고, 모든 역할을 같은 모델로 묶어야 했고, 어느 실행이 어디서 멈췄는지는 끝난 뒤 기록을 읽어야 알았다. 도구마다 이 중 하나를 겨냥하므로, 풀려는 문제를 먼저 정하면 그 도구를 붙였을 때 비교 조건 중 무엇이 바뀌는지도 미리 안다.

### 무엇인가

에이전트 팀(Agent Teams): 컨텍스트 끊김을 겨냥한 Claude Code의 실험 기능. 팀원(teammate) 하나하나가 독립된 세션으로 서로에게 직접 메시지를 보내고, 공유 작업 목록에서 다음 일을 스스로 가져간다. 조율 주체가 바뀌므로 C와 비교하려면 기준선을 다시 세운다.

Workflows: 재현 문제를 겨냥한 Claude Code 기능. B에서 사람이 파이썬으로 적었던 순서를 Claude가 자바스크립트로 쓰고, 런타임(스크립트 실행을 맡는 프로그램)이 백그라운드에서 돌린다. 반복·분기와 중간 결과는 스크립트 안에 머물고 Claude의 컨텍스트엔 최종 결과만 들어온다. 실행마다 스크립트와 결과가 남고, 같은 세션에서 다시 돌리면 끝난 에이전트는 저장된 결과를 돌려주고 프롬프트가 바뀐 에이전트부터 다시 실행한다. 스크립트 안에서 현재 시각·난수를 쓰면 오류를 내 같은 순서가 반복되게 한다. 실행 중엔 사람이 끼어들 수 없으며, B와 같은 방식이라 바로 비교할 수 있다.

oh-my-claudecode: 모델 배분 문제를 겨냥한 커뮤니티 오케스트레이션 프레임워크(2026년 10월 기준 GitHub 별 약 4만 개). 기본으로 단순 조회는 Haiku, 표준 구현은 Sonnet, 설계·깊은 분석은 Opus에 맡긴다. 실행 모드 ralph는 검증을 통과할 때까지 수정을 반복해, 검증_성실성 점수가 물은 것을 도구가 강제한다. 다만 프레임워크가 자체 프롬프트를 끼워 넣어 차이의 원인을 가르기 어렵다.

herdr: 상태 가시성 문제를 겨냥한 오픈소스 런타임. 백그라운드 서버가 에이전트 CLI의 터미널을 소유해 터미널을 닫거나 SSH(원격 접속)가 끊겨도 작업이 이어지고, 창마다 작업 중(working)·대기(blocked)·유휴(idle) 상태를 표시하며, 코딩 에이전트 CLI 20여 종을 한 화면에 둔다. 결과를 판정하지는 않는다. '유휴'는 끝났다는 뜻이지 테스트 통과가 아니다. 비교 조건을 바꾸지 않아 오늘 실험에 그대로 더할 수 있다.

**문제로 도구를 고르는 표**

| 오늘 실험이 남긴 문제 | 겨냥한 도구 | 바뀌는 것 | 남는 한계와 비교 조건 |
|---|---|---|---|
| 컨텍스트가 끊긴다 | 에이전트 팀 | 누가 다음 행동을 정하나 | 토큰이 팀원 수에 비례, 대화형 세션 전용, 기준선 재설정 |
| 재현이 안 된다 | Workflows | 누가 다음 행동을 정하나 | 실행 중 사람 개입 불가, B와 바로 비교 |
| 모델을 나누기 어렵다 | oh-my-claudecode | 어느 모델이 하나 | 프레임워크 프롬프트가 섞여 원인 분리 어려움, 고정 조건에 역할별 모델 열 추가 |
| 상태가 안 보인다 | herdr | 어디서 지켜보나 | 결과 판정은 안 함, 비교 조건 그대로 |

### 정리하면

- 네 도구는 서로를 대체하지 않는다. 조율 주체나 모델이 바뀌면 기준선을 다시 세우지만 비교 방법은 같다. 조건을 고정하고, 기록을 남기고, 같은 방식으로 읽는다.
- Workflows에서 한 번 실행에 에이전트 25개나 150만 토큰을 넘을 것 같으면 큰 실행 경고가 뜨지만, 알림일 뿐 멈추지는 않는다.

### 배운 것

- 스텝 9 · 실험에서 드러난 문제와 관련 도구: 실험이 남긴 네 문제(컨텍스트 끊김·재현 불가·모델 배분·상태 불가시)와 각각을 겨냥한 도구(에이전트 팀·Workflows·oh-my-claudecode·herdr), 그리고 도구가 '누가 정하나/어느 모델/어디서 지켜보나' 중 무엇을 바꾸는지에 따라 기준선을 다시 세울지 정한다는 것을 배웠다.

관련 항목: 에이전트 팀, 멀티 에이전트, A·B·C 비교 실험, 서브에이전트

## 에이전트 팀 (Agent Teams · Claude Code 실험 기능)

Claude Code에서 여러 팀원 세션이 서로 직접 메시지를 주고받고, 공유 작업 목록에서 일을 스스로 가져가게 하는 실험 기능.

### 왜 필요한가

서브에이전트는 결과를 리드에게만 돌려주고 끝나서, 워커가 둘이면 서로 무엇을 찾았는지 모른다(Cognition이 지적한 문제). 팀원끼리 직접 대화하게 하면 이 끊김이 줄어든다.

### 무엇인가

서브에이전트는 리드가 일을 맡기고 결과를 리드에게 돌려준 뒤 끝난다. 에이전트 팀의 팀원은 각자 컨텍스트 윈도우를 가진 독립 세션으로 서로에게 직접 메시지를 보내고, 공유 작업 목록에서 다음 일을 스스로 가져간다. 파일 잠금으로 같은 작업을 둘이 동시에 가져가지 않게 막는다.

공식 문서 사례: 원인 모를 버그를 두고 팀원 다섯이 각자 다른 가설을 맡아 서로 반박하게 해, 한 에이전트가 첫 가설에 묶이는 문제를 줄였다.

**undefined**

| 항목 | 서브에이전트 | 에이전트 팀의 팀원 |
|---|---|---|
| 결과 전달 | 결과를 리드에게 돌려주고 끝남 | 독립 세션으로 서로에게 직접 메시지 |
| 일을 가져가는 방식 | 리드가 맡김 | 공유 작업 목록에서 스스로 가져감(파일 잠금으로 중복 방지) |

### 정리하면

- 켜는 법: settings.json의 env 항목에 CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS 를 "1"로 넣는다.
- 감수할 점: ① 팀원 하나 = Claude 세션 하나라 토큰이 팀원 수에 비례해 늘어난다 ② 세션당 팀 하나이고 팀원이 다시 팀을 만들 수 없다 ③ 대화형 세션에서만 팀원이 생긴다. Agent SDK로 돌리면 켜 둬도 서브에이전트로 실행되어 오늘 실험에 바로 넣을 수 없다.
- Claude Code의 .claude/agents/ 서브에이전트 정의 파일은 팀원 정의로도 재사용할 수 있다.

### 배운 것

- 스텝 9 · 컨텍스트가 끊기는 문제 → 에이전트 팀: 에이전트 팀의 팀원이 서브에이전트와 달리 서로 직접 메시지를 보내고 공유 작업 목록에서 일을 가져간다는 것, 켜는 법(CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1)과 세 가지 제약(토큰 비례 증가, 세션당 팀 하나, 대화형 세션 전용)을 배웠다.

관련 항목: 서브에이전트, 멀티 에이전트 보조 도구, 멀티 에이전트

## 채택 · 축소 · 폐기 (멀티 에이전트 적용 판정)

A·B·C 실험 결과를 근거로, 이 조건에서 멀티 에이전트를 쓸지(채택), 일부에만 쓸지(축소), 쓰지 않을지(폐기)를 정하는 판정.

### 왜 필요한가

실험을 하고 '좋았다/나빴다'로 끝내면 다음 결정에 쓸 수 없다. 어떤 결과 파일의 어느 행을 근거로, 어떤 한계 안에서 결론을 냈는지 적어야 남이 검토하고 다시 확인할 수 있다.

### 무엇인가

채택은 이 조건에서 멀티 에이전트 구성(B 또는 C)을 쓴다는 뜻이다. 축소는 일부 단계·일부 문제에만 나눠 쓴다는 뜻이다(예: 탐색이 많은 문제에서만 locator에게 탐색을 맡김). 폐기는 나누지 않고 A처럼 에이전트 하나로 처리한다는 뜻이다.

과제의 목표는 세 가지다. ① 고정할 조건, 바꿀 조율 방식, 측정할 값을 실행 전에 구분한다 ② result.json·grading.jsonl·results-table.md에서 근거를 찾아 연결한다 ③ 이 조건에서만 결론을 말하고 다시 확인할 조건을 밝힌다.

**평가 루브릭**

| 루브릭 | 충족 조건 |
|---|---|
| 고정·조작·측정의 분리 | 같은 인스턴스·모델·저장소 준비·채점 조건과 A·B·C의 조율 방식을 구분하고, 해결 여부·비용·턴·시간·행동 판정을 측정값으로 제시 |
| 결과 파일 근거의 연결 | result.json·grading.jsonl·results-table.md의 행 또는 인용을 판정문과 연결하고, evidence_quote는 원래 트랜스크립트로 다시 확인 |
| 결론의 적용 조건 | 턴 예산 차이와 경량 평가라는 한계를 밝히고, 이 조건에서만 결론을 말함 |

### 정리하면

- results-table.md의 숫자를 그대로 믿지 말고 각 행을 result.json·grading.jsonl로 거슬러 확인한다.
- 턴 예산이 A·B·C에서 다르므로 구조 일반의 우열은 말할 수 없다. '말할 수 있는 것'(SymPy 3문제·이 조건의 기록)과 '말할 수 없는 것'(다른 문제·다른 예산에서도 같다는 것)을 나눠 적는다.

```
이 조건에서는 [채택·축소·폐기]합니다. [결과 파일의 근거]가 있고, [비용·시간·턴 또는 판정 기록]이라는 한계가 있기 때문입니다.
```
판정문 틀. 다시 실행한다면 고정할 조건과 바꿀 조건도 함께 적는다.

### 배운 것

- 스텝 10 · 채택·축소·폐기 판정과 과제: 채택·축소·폐기 세 판정의 뜻, 과제의 세 목표(조건 분리·결과 파일 근거 연결·결론 범위), 세 항목 루브릭과 판정문 틀을 배웠다.

관련 항목: A·B·C 비교 실험, 멀티 에이전트
